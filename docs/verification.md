# Результати фінальної локальної перевірки

Перевірено 2026-11-06. Після огляду користувач погодив публікацію:
[GitHub-репозиторій](https://github.com/Qwerty-polo/ai-first-support-service).
Публічне тимчасове демо розгорнуто на EC2 після погодження користувача:
[інтерфейс](https://support-demo-13-49-224-87.sslip.io/operator/).

## Автоматичні перевірки

- pytest на PostgreSQL: 92 тести пройдено за 39.80 с на Windows, без пропусків і без SQLite.
- Повторення всього набору в Linux-контейнері: 92 тести за 31.61 с, ті самі 98.70%.
  Dev-залежності встановлено з `uv.lock` у тимчасове середовище контейнера;
  тести використовували власні випадково названі БД. Контейнер після тестів видалений.
- Coverage: 98.70% сумарно для рядків і розгалужень усіх модулів `app`;
  рядки — 594/599, гілки — 90/94. Непокриті частини не приховані через omit.
  `htmlcov/index.html` і `coverage.xml` генеруються локально, поза Git.
- Строгий mypy: усі 16 модулів `app` проходять перевірку.
- Ruff check та Ruff format check.
- Alembic upgrade із порожньої БД та check на відповідність моделям.
- Невалідний Unicode CSRF-токен тепер дає 403 замість 500; додано регресійну перевірку.
- Git не відстежує `.env`, ключі, `.venv*`, `.idea` чи QA-скриншоти.

Повторний аудит знайшов і виправив передчасний `failed` при тимчасовій помилці БД
усередині handler. Регресійні тести підтверджують retry, наступний успіх, облік нового
LLM-допуску та відсутність приватних деталей помилки в логах.

Додано повний workflow через справжні HTTP-маршрути та HTML CSRF-форму з контрольованим
LLM, approve/reject, повторним approve й 503 від helpdesk. Перевірено запуск worker
через його `main()`, генерацію та закриття HTTP-клієнта при скасуванні. Доставка
продовжує працювати, коли всі 60 LLM-допусків уже використані.

## Відповідність вимогам

| Вимога | Реалізація | Автоматичні докази |
|---|---|---|
| Швидкий надійний webhook, дублікати | Унікальний event_id, подія + job одним commit | `test_webhook.py`: паралельні API, rollback, restart, outage, timeout |
| 500 звернень без втрат | Durable jobs у PostgreSQL | `test_capacity.py`: 500 різних + 50 дублікатів, повне опрацювання |
| Повільний LLM поза webhook | Окремий worker | `test_generation.py`, `test_workflow.py` |
| 60/хв на весь сервіс | Спільний admission ledger, включно з retries | `test_worker.py`: конкурентність, межа й звільнення бюджету |
| Відновлення після збою | Lease, token, bounded retry | `test_worker.py`: cancellation, stale result, expiry, DB outage |
| Без ключа теж HTTP + затримка | Реальний POST, fallback і загальний часовий бюджет | `test_llm.py`: виклик, затримка, помилки, зависання |
| Статті й реальні citations | Дев'ять статей, перевірка ID, серверні URL | `test_llm.py`, `test_generation.py` |
| Модерація перед відправленням | Atomic approve/job; reject без доставки | `test_operator.py`, `test_delivery.py`, `test_workflow.py` |
| 201, 5xx, timeout, без дубля | Адаптер і стабільний ключ, надійний мок | `test_delivery.py`: одночасні дублікати, втрачений ACK, restart |
| `/health`, PostgreSQL, Compose | Liveness, Alembic, окремі процеси | `test_health.py`, міграції fixture, перевірки Compose нижче |
| Інструкції й конфігурація агента | README, docs, AGENTS, Git-історія | Опубліковані на GitHub з оригінальною історією без squash |

GitHub Actions виконує для push/PR Ruff, mypy, міграції й PostgreSQL-тести,
мінімум 90% coverage та HTML/XML artifact. Перший віддалений запуск успішний:
[Checks #1](https://github.com/Qwerty-polo/ai-first-support-service/actions/runs/42134099067).
Поточний результат показаний у README та на вкладці Actions.
Налаштування coverage явно враховує greenlet;
перший пробний звіт без цього параметра мав неточні дані для async SQLAlchemy.

## Перевірка обсягу

`tests/test_capacity.py`: 550 запитів при конкурентності 10, серед них 500 різних
подій та 50 дублікатів. Збережено рівно 500 подій і 500 generation jobs.
На цій машині p95 приймання — 58 мс, максимум — 126 мс; вимір через ASGITransport
без зовнішньої мережі. Це локальний результат, не гарантія часу для довільного хостингу.

Два worker з контрольованим LLM обробили всі 500 jobs. На кожне вікно дозволено
не більше 60 допусків. Межі вікон прискорювалися переведенням timestamps лише в
тимчасовій тестовій БД; це не десятихвилинний production benchmark.
Реальні платні LLM-запити під час масових перевірок не виконувалися.

## Чистий Compose та браузер

Створено окрему копію відстежуваних файлів без `.env`, `.git` і локальних середовищ.
Compose запущено під окремим project name з новим PostgreSQL volume та окремими портами.
Міграції, API, worker і mock-helpdesk стартували успішно.

Після повторного аудиту основний Compose перебудовано й запущено з оновленим кодом.
Наявний volume і демонстраційні звернення збережено.

Перевірено: вебхук → реальна безключова спроба LLM → чернетка → HTML-форма approve
→ доставка з `accept-timeout` → одна прийнята відповідь. Основну БД не очищали;
після перевірки видалено лише тимчасові контейнери й том окремого project name.

У headless Microsoft Edge відкрито інтерфейс із чернеткою на ширині 1280 та 390 px.
Скриншоти обох розмірів переглянуто: читабельний текст, доступні кнопки, немає
горизонтального overflow або JavaScript-помилок. Скриншоти залишені поза Git.

## Межі перевірки

Публічний HTTPS-сценарій також перевірено 2026-11-06:

- TLS-сертифікат перевірено з сервера та зовнішнього комп'ютера без вимкнення TLS validation.
- Неавторизований оператор отримує 401; вебхук приймається та дедуплікується.
- Реальна безключова генерація, approve через HTML CSRF-форму двічі,
  `accept-timeout`, успішний повтор доставки й рівно одна receipt.
- Reject через HTML-форму двічі, жодного повідомлення в моку.
- Залишено три непідтверджені штучні звернення для ручного огляду.
- Демо споживає близько 245 МБ RAM; встановлені межі пам'яті й CPU.
  Немає OOM або перезапусків контейнерів після smoke-перевірки.
- На спільному сервері ID всіх шести контейнерів наявного проєкту залишилися
  незмінними; його публічна сторінка повертала HTTP 200 до й після розгортання.
- Caddy-конфігурація збережена в приватній резервній копії, старі маршрути перевірені
  на незмінність; застосовано graceful reload, без restart вебсервера.

Масове навантаження на спільному EC2 не запускалося. Наявні дані іншого проєкту
не змінювалися, а нове демо має власні мережу, БД, volume і секрети.

- Платний OpenAI-режим перевірений контрольованими HTTP-відповідями; доступність моделі
  з ключем власника акаунта не перевірялася. Безключовий режим перевірено реально.
- Відсутність дубля після таймауту залежить від надійного Idempotency-Key на стороні
  хелпдеску. Мок його реалізує; довільне зовнішнє API може не підтримувати цю гарантію.
- Глобальний ліміт у БД стосується допусків до LLM-обробника; довільна пауза ОС між
  допуском і HTTP-викликом може змінити фактичний час запиту.
- Перед публічним деплоєм потрібні власні секрети, HTTPS, правильний PUBLIC_BASE_URL
  та довірений allowlist.
