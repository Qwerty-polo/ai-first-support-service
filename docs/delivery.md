# Доставка та мок хелпдеску

Worker відправляє `POST reply_url` із JSON `ticket_id`, `message` та заголовком
`Idempotency-Key: delivery:<job UUID>`. Текст береться зі знімка, створеного при approve.
Успіх — лише HTTP 201; 5xx, 408, 429 та мережеві таймаути повторюються через queue.
Інші статуси завершують job помилкою. Бюджет одного HTTP-виклику — 5 секунд.
Максимум три спроби; після вичерпання помилка видима оператору.

Адресу перевіряємо при прийманні вебхука та перед доставкою: точний origin
(схема, hostname, порт) із JSON-масиву `ALLOWED_REPLY_ORIGINS`.
Default Compose — `["http://mock-helpdesk:8000"]`. Для локального API/worker поза Docker
задайте `["http://127.0.0.1:8002"]` і відповідний reply_url. Credentials, fragments і
неоднозначні URL заборонені; redirects та environment proxies вимкнені.
Дозволені hostname контролює власник конфігурації; не додавайте недовірені домени.

`HELPDESK_API_TOKEN` передається як Bearer-токен; mock перевіряє його.
Default `local-mock-token` — лише локальне демо. HTTPX request logs вимкнені,
щоб query-параметри URL не потрапляли до журналів.

Мок надійно зберігає ключ, ticket_id та message у `mock_receipts` однією транзакцією.
Цей запис представляє доставлене клієнту повідомлення. Повтор повертає 201, а зміна
payload під тим самим ключем — 409. Дані переживають перезапуск процесу.
Мок використовує ту саму PostgreSQL-інстанцію, окремі таблиці; це спрощує локальний запуск.

Сценарій задається query-параметром у reply_url:

| scenario | Поведінка |
|---|---|
| normal | Зберігає відповідь і повертає 201 |
| fail-once | Перша спроба — 503, наступна — 201 |
| always-500 | Кожна спроба — 503 |
| timeout-before | Перша спроба чекає 8 с без приймання, повтор приймається |
| accept-timeout | Зберігає відповідь, затримує перший 201 на 8 с; повтор одразу повертає 201 |

Приклад: `http://mock-helpdesk:8000/tickets/T-1042/replies?scenario=accept-timeout`.
Лічильники спроб зберігаються в `mock_attempts` і переживають перезапуск.
Отримані повідомлення можна переглянути через `http://localhost:8002/messages/T-1042`
із HTTP Basic входом оператора. `/health` мока публічний.

**Межа гарантії:** відсутність дубля після невизначеного HTTP-результату забезпечують
стабільний ключ і надійна підтримка цього ключа хелпдеском. Для стороннього API без
ідемпотентності гарантувати це неможливо. `failed` після таймаутів не доводить, що
зовнішній сервіс нічого не прийняв: потрібна звірка за ключем, а не новий job із новим ID.

Тести перевіряють конкурентні дублікати, конфлікт payload, відновлення мока,
втрату підтвердження після приймання, правила статусів і відсутність неавторизованих доставок.

Наскрізна перевірка в Compose: реальний вебхук, безключова генерація за 16.2 с,
два підтвердження через HTML-форму, scenario=accept-timeout. Worker зробив дві спроби
з одним ключем, отримав успіх, у моку залишилася рівно одна прийнята відповідь.
Актуальний загальний набір і coverage наведено в [verification.md](verification.md).
