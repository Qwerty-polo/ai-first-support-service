# Рішення та межі гарантій

## Надійність через PostgreSQL

Подію та generation job зберігаємо однією транзакцією. Після commit вебхук швидко
повертає успіх. Унікальний `event_id` захищає від одночасних дублікатів.
SELECT перед INSERT не замінює унікальне обмеження. За недоступної БД повертаємо помилку,
щоб хелпдеск повторив доставку. Успіх означає збереження, а не завершену генерацію.

Окремий worker захоплює jobs через `FOR UPDATE SKIP LOCKED`, призначає
lease token і строк оренди та завершує транзакцію перед зовнішнім запитом.
Оновлення результату можливе лише для чинного token. Прострочені jobs можна захопити
повторно; застарілий worker не має перезаписати новіший результат.
Стани, спроби, наступний запуск і остання безпечна помилка зберігаються в БД.
Redis, Celery і RabbitMQ не потрібні для цього масштабу.

Ліміт LLM реалізовано в БД як спільний ковзний інтервал 60 секунд із серіалізованим
отриманням дозволу. Усі процеси й повтори користуються одним механізмом.
Окремо обмежуємо активні виклики спільними слотами. Остаточний SQL і відновлення
слотів перевірено на PostgreSQL на етапі worker. Активний слот — running job із чинною орендою.

## Доставка та ідемпотентність

Approve і створення delivery job відбуваються атомарно, з унікальністю job для чернетки.
Повторне натискання не створює нову доставку. Reject не створює доставку.

Припущення інтеграції: хелпдеск підтримує `Idempotency-Key`, стабільний для однієї
доставки. Наш мок надійно зберігає ключ, payload та результат у PostgreSQL.
Прийом повідомлення та запис ключа мають бути атомарними. Повтор із тим самим
ключем і payload повертає збережений успіх; інший payload із тим самим ключем — конфлікт.
Мок моделює «прийнято, але HTTP-підтвердження загубилося».

Для довільного API без такої підтримки локальна БД не гарантує відсутності дублікатів:
після таймауту неможливо визначити, чи зовнішня сторона вже виконала дію.
Ця можливість не описана роботодавцем, тому це явне припущення, а не вимога з DOCX.

## Простота інтеграцій

FastAPI + SQLAlchemy async + asyncpg; Alembic керує схемою.
HTTPX-адаптери LLM і хелпдеску приймають підмінні залежності для тестів.
Пошук за словами по 5–10 статтях, Jinja2 для простого UI. Векторна БД не потрібна.
OpenAI — обраний провайдер, модель задається налаштуванням.
Вихідні citations перевіряються за списком реально знайдених статей.

Після аудиту пошук також передається як типізована функція в `GenerationHandler`.
`DraftGenerator` і `HelpdeskSender` описують контракти інтеграцій; `worker.main()`
обирає реалізації. Для цього обсягу окремі DI-контейнер і repository layer не потрібні.
Приклади розширення й аргументи — у [architecture.md](architecture.md).

## Основа і запуск

Python 3.13.15 локально й у Docker. Залежності повністю зафіксовано в `uv.lock`;
`uv sync --locked` перевіряє відповідність маніфесту. Docker використовує uv 0.12.10.
Образи мають явні теги; digest-pinning наразі не зроблено.
Локальне середовище `.venv313` не зачіпає стару `.venv`.

`/health` — liveness процесу: повертає 200 і `{"status":"ok"}` без SQL-запиту.
Готовність БД перевіряє `pg_isready`; API запускається після успішної міграції.
Окремий одноразовий `migrate` у Compose запобігає запуску Alembic кожним API-процесом.
Baseline не створює предметних таблиць; міграція `0002_events_jobs` додає події й jobs.
Worker і mock-helpdesk працюють як окремі процеси Compose зі спільним кодом.

Compose публікує порти тільки на localhost. Пароль БД `support` — локальна demo-конфігурація.
Для публічного деплою потрібні окремі секрети, захист дій оператора та allowlist reply URL.
Тіла звернень і секрети не логуються; HTTP access logs Uvicorn вимкнені.

## Реалізація приймання події

Обидва успішні результати (`accepted` і `duplicate`) повертають 202 після перевірки БД.
Повтор із тим самим `event_id`, але іншим нормалізованим payload — 409 без перезапису.
Це наше рішення для некоректного повторного використання ключа, не вимога роботодавця.
При збої збереження — 503 із Retry-After, без тексту SQL чи параметрів у логах.
Таймаут обробки 1.5 с, connect/command timeout 1 с, pool timeout 0.3 с.
Захист 2 с перевірено для успішного приймання, відмови з'єднання та блокування таблиці;
це не абсолютна гарантія повного HTTP-часу за довільної мережі або зависання ОС.

Збереження використовує `ON CONFLICT DO NOTHING ... RETURNING` і унікальний PK.
Другий запит із дублем чекає завершення конфліктної транзакції, а потім звіряє вміст.
Jobs мають унікальність `(event_id, kind)` та індекс `(state, available_at)` для worker.
Міграція `0003_worker` додає lease token, lease deadline, результат та код помилки.
Для локального підключення обрали IPv4 `127.0.0.1`, оскільки `localhost` на цій Windows
спочатку пробує недоступний IPv6 і вичерпує короткий connection timeout.

## Виконання фонового завдання

Оренда фіксована: 60 с, timeout обробника: 40 с. Heartbeat не потрібен для очікуваних
викликів 5–30 с; це спрощує реалізацію. Async-обробник має коректно скасовуватися.
Власник записує результат лише за збігу token, running state та чинного lease.
Після падіння повторне захоплення видає новий token, а попередній результат відхиляється.
Після третьої простроченої оренди job стає failed. Результат зберігається в JSONB jobs.result;
операторський інтерфейс читає чернетку з цього збереженого результату.

Допуск до генерації серіалізовано рядком llm_policy. На один допуск дозволено один
зовнішній запит, включно з безключовим режимом. Внутрішні HTTP-retry адаптера заборонені:
повтор проходить через нове захоплення й витрачає новий допуск. Довільне зависання ОС
між допуском і HTTP-запитом не можна перетворити на гарантію точного часу запиту провайдера;
обмеження БД точно стосується допусків, а інтеграція має мінімізувати цю затримку.
Типова глобальна concurrency=32, local worker parallelism=32. Worker підключає generation
і delivery обробники.

## LLM та джерела

Дев'ять статей LumaDesk зберігаються як незмінні типізовані записи в коді; окрема БД
для такого обсягу не потрібна. Пошук за ключовими словами повертає до трьох статей.
За відсутності збігів передаємо лише статтю про уточнення питання й позначаємо це в результаті.
Доступні `/kb/{id}` і абсолютні посилання на основі PUBLIC_BASE_URL.

Вибір реалізації: OpenAI Responses API, попередня модель `gpt-4.1-mini` з налаштування.
Точний формат перевірено в офіційній документації; доступ до моделі з ключем власника
не перевірявся. Безключовий шлях реально звертається до того самого endpoint, не передає
даних клієнта, переживає HTTP-помилки та використовує статичний текст за релевантною статтею.
Три секунди мережевого бюджету входять у загальну змодельовану затримку 5–30 секунд.

Structured Outputs спрощує парсинг, але відповідь усе одно валідується локально.
ID джерел мають належати переданим статтям, а URL від моделі не використовуються.
Посилання додає сервер. Це гарантує існування джерел, а не семантичну безпомилковість
тексту; підтвердження оператором залишається обов'язковим.

Наскрізна перевірка етапу: Docker-worker реально отримав 401 від OpenAI без ключа,
зберіг статичну чернетку через 16.3 с, посилання на PDF-статтю повернуло HTTP 200.
Платний режим перевірений через контрольовані HTTP-відповіді; витратних викликів не було.

## Рішення оператора

Простий Jinja2 UI з HTTP Basic, 25 зверненнями на сторінку та явним оновленням.
HMAC CSRF-токен підписує пару (job UUID, action) ключем оператора; авторизація потрібна
як для читання, так і для дій. Autoescape захищає від HTML у повідомленнях і чернетках.
Локальний пароль демонстраційний; перед публікацією потрібні власний пароль та HTTPS.

Рішення pending/approved/rejected живе на події, окремо від технічного стану job.
Транзакція SELECT FOR UPDATE блокує звернення, перевіряє готовність чернетки та
зберігає рішення разом із delivery job. Текст фіксується в jobs.payload.message.
Повтор тієї самої дії повертає успіх; протилежне рішення — 409. Немає редагування
тексту чи скасування вже підтвердженого надсилання: це тримає сценарій компактним.
Міграція 0004_review додає поля рішення й delivery payload.

## HTTP-доставка

DeliveryHandler повторно перевіряє approved та чинний lease, копіює дані й закриває
сесію до HTTP. Ключ `delivery:<job UUID>` однаковий після будь-якого повтору чи reclaim.
Приймається лише 201; 5xx/408/429 і таймаути повторюються в межах трьох спроб.
Origin URL перевіряється на вході та перед HTTP, redirects вимкнені.

Міграція 0005_mock_receipts додає надійний журнал прийнятих повідомлень мока.
Унікальний ключ і payload записуються атомарно; сама receipt представляє side effect.
Сценарій accept-timeout затримує відповідь після commit. Це дозволяє перевірити,
що повтор через втрату підтвердження не створює другої receipt.
Конфігурацію та межі гарантій описано в docs/delivery.md.

## Повторний аудит і автоматичні перевірки

Помилка з'єднання з БД усередині handler тепер проходить bounded retry, як і збій
провайдера. Раніше вона могла потрапити в загальний except та одразу завершити job.
Якщо сама фіксація retry також не вдається, залишається чинний lease для відновлення.
Додані перевірки обох рівнів: збій handler і збій claim у безперервному циклі worker.

Весь `app` перевіряється строгим mypy. Для SQL із гарантовано одним рядком застосовано
`scalar_one()` замість неявного припущення про non-None. Coverage рахує також гілки
і перемикання greenlet, які потрібні SQLAlchemy async. Поріг 90% фіксує мінімум для
регресій; конкретне число не замінює перевірку бізнес-інваріантів.
