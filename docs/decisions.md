# Рішення та межі гарантій

## Надійність через PostgreSQL

Подію та generation job зберігатимемо однією транзакцією. Після commit вебхук швидко
повертає успіх. Унікальний `event_id` захищає від одночасних дублікатів.
SELECT перед INSERT не замінює унікальне обмеження. За недоступної БД повертаємо помилку,
щоб хелпдеск повторив доставку. Успіх означає збереження, а не завершену генерацію.

Окремий worker захоплюватиме jobs через `FOR UPDATE SKIP LOCKED`, призначатиме
lease token і строк оренди та завершуватиме транзакцію перед зовнішнім запитом.
Оновлення результату можливе лише для чинного token. Прострочені jobs можна захопити
повторно; застарілий worker не має перезаписати новіший результат.
Стани, спроби, наступний запуск і остання безпечна помилка зберігаються в БД.
Redis, Celery і RabbitMQ не потрібні для цього масштабу.

Ліміт LLM реалізуємо в БД як спільний ковзний інтервал 60 секунд із серіалізованим
отриманням дозволу. Усі процеси й повтори користуватимуться одним механізмом.
Окремо обмежимо активні виклики спільними слотами. Остаточний SQL і відновлення
слотів перевіримо на етапі worker; зараз ці механізми ще не реалізовані.

## Доставка та ідемпотентність

Approve і створення delivery job відбудуться атомарно, з унікальністю job для чернетки.
Повторне натискання не створює нову доставку. Reject не створює доставку.

Припущення: мок хелпдеску підтримуватиме `Idempotency-Key`, стабільний для однієї
доставки, і надійно зберігатиме ключ, payload та результат у PostgreSQL.
Прийом повідомлення та запис ключа мають бути атомарними. Повтор із тим самим
ключем і payload повертає збережений успіх; інший payload із тим самим ключем — конфлікт.
Мок моделюватиме «прийнято, але HTTP-підтвердження загубилося».

Для довільного API без такої підтримки локальна БД не гарантує відсутності дублікатів:
після таймауту неможливо визначити, чи зовнішня сторона вже виконала дію.
Ця можливість не описана роботодавцем, тому це явне припущення, а не вимога з DOCX.

## Простота інтеграцій

FastAPI + SQLAlchemy async + asyncpg; Alembic керує схемою.
HTTPX-адаптери LLM і хелпдеску прийматимуть підмінні залежності для тестів.
Пошук за словами по 5–10 статтях, Jinja2 для простого UI. Векторна БД не потрібна.
OpenAI попередньо обраний провайдер, модель задаватиметься налаштуванням перед інтеграцією.
Вихідні citations перевірятимуться за списком реально знайдених статей.

## Основа і запуск

Python 3.13.15 локально й у Docker. Залежності повністю зафіксовано в `uv.lock`;
`uv sync --locked` перевіряє відповідність маніфесту. Docker використовує uv 0.12.10.
Образи мають явні теги; digest-pinning наразі не зроблено.
Локальне середовище `.venv313` не зачіпає стару `.venv`.

`/health` — liveness процесу: повертає 200 і `{"status":"ok"}` без SQL-запиту.
Готовність БД перевіряє `pg_isready`; API запускається після успішної міграції.
Окремий одноразовий `migrate` у Compose запобігає запуску Alembic кожним API-процесом.
Baseline не створює предметних таблиць; міграція `0002_events_jobs` додає події й jobs.
Worker і mock-helpdesk додамо до Compose тоді, коли вони виконуватимуть корисну роботу.

Compose публікує порти тільки на localhost. Пароль БД `support` — локальна demo-конфігурація.
Для публічного деплою потрібні окремі секрети, захист дій оператора та allowlist reply URL.
Тіла звернень і секрети не логуються; HTTP access logs Uvicorn вимкнені.

## Реалізація приймання події

Обидва успішні результати (`accepted` і `duplicate`) повертають 202 після перевірки БД.
Повтор із тим самим `event_id`, але іншим нормалізованим payload — 409 без перезапису.
Це наше рішення для некоректного повторного використання ключа, не вимога роботодавця.
При збої збереження — 503 із Retry-After, без тексту SQL чи параметрів у логах.
Таймаут обробки 1.5 с, connect/command timeout 1 с, pool timeout 0.3 с.
Захист 2 с перевірено для успішного приймання, відмови з'єднання та блокування таблиці;
це не абсолютна гарантія повного HTTP-часу за довільної мережі або зависання ОС.

Збереження використовує `ON CONFLICT DO NOTHING ... RETURNING` і унікальний PK.
Другий запит із дублем чекає завершення конфліктної транзакції, а потім звіряє вміст.
Jobs мають унікальність `(event_id, kind)` та індекс `(state, available_at)` для worker.
Поля lease/fencing додамо на етапі worker разом із перевіркою відновлення.
Для локального підключення обрали IPv4 `127.0.0.1`, оскільки `localhost` на цій Windows
спочатку пробує недоступний IPv6 і вичерпує короткий connection timeout.
