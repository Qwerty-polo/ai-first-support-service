# Специфікація тестового завдання

Джерело вимог: документ роботодавця «Тестове завдання: AI-first Backend Engineer»
(прочитано повністю 2026-11-05). Цей файл відділяє вимоги роботодавця від наших рішень.
Оригінальний DOCX не додаємо до репозиторію; нижче зафіксовано всі його суттєві вимоги.

## Вимоги роботодавця

Сервіс приймає звернення підтримки, знаходить релевантні статті, генерує LLM-чернетку
з посиланнями, показує її оператору та надсилає клієнту лише після підтвердження.
Оператор може відхилити чернетку. Вебінтерфейс простий, дизайн не є пріоритетом.

Вебхук: `POST /webhooks/helpdesk`, JSON:

```json
{
  "event_id": "evt_8f2a",
  "ticket_id": "T-1042",
  "customer_email": "user@example.com",
  "message": "Не можу експортувати звіт у PDF",
  "reply_url": "https://helpdesk.example.com/tickets/T-1042/replies"
}
```

- Хелпдеск чекає максимум 2 секунди, потім повторює доставку.
- Одна подія може надходити повторно та одночасно.
- Зазвичай кілька звернень на хвилину, пік — 500 за 10 хвилин. Звернення не можна втрачати.
- Надсилання: `POST <reply_url>` з `ticket_id` та `message`; успіх лише `201 Created`.
- API хелпдеску може повертати `5xx` або відповідати із запізненням.
  Однакова відповідь не має надсилатися клієнту двічі.
- Справжнього хелпдеску немає: потрібен простий мок.
- `/health` повертає HTTP 200.
- LLM-провайдер і модель довільні; один виклик триває 5–30 секунд.
- Ліміт LLM — 60 запитів на хвилину на весь сервіс.
- Без API-ключа сервіс усе одно робить реальний запит до провайдера, але використовує
  статичну відповідь із затримкою 5–30 секунд. Решта сценарію працює так само.
- База знань: 5–10 коротких AI-згенерованих статей про вигаданий продукт;
  спосіб зберігання та пошуку довільний.
- Python, FastAPI або Django; PostgreSQL; запуск через `docker compose up`.
- Здати GitHub-репозиторій з історією без squash, детальний README та використану
  конфігурацію агента, правила і специфікації.
- Публічний деплой із URL вебхука й інтерфейсу дуже бажаний, але необов'язковий.
- Орієнтовна тривалість роботи за оцінкою роботодавця: 3–4 години.

## Додаткові домовленості з користувачем

- Компактні завершені етапи з поясненнями українською; пауза після основи.
- Python 3.13 локально і в Docker; наявну `.venv` Python 3.14 не видаляти.
- Типізація, короткі пояснювальні коментарі, тести разом із функціоналом.
- Без ключа: обмежити реальний HTTP-запит таймаутом, переживати відмову провайдера,
  після чого повертати статичний результат у межах очікуваної затримки.
- Захист оператора та allowlist `reply_url` перед публічним розгортанням.
- Платні зовнішні дії та публікацію погодити після підготовки результату.
- Дедлайн уточнено як 24 години; робочий орієнтир — 2026-11-06 близько 19:15 за Києвом.

## Етапи та перевірки

1. **Основа (завершено):** правила, специфікація, рішення, lockfile, налаштування,
   FastAPI `/health`, SQLAlchemy, Alembic baseline, Docker та PostgreSQL. Пауза для огляду.
2. **Вебхук (завершено):** атомарне збереження події й завдання, унікальний `event_id`, конкурентні дублікати,
   відповідь без очікування LLM; помилка БД не повинна виглядати як успішний прийом.
3. **Worker (механіка завершена):** короткі транзакції, конкурентне захоплення, leases, fencing, відновлення,
   backoff, межі спроб, глобальний ліміт LLM і окремий ліміт одночасних викликів.
4. **Генерація (завершено):** статті, пошук, адаптер LLM, реальний і безключовий режими, перевірка посилань.
5. **Модерація (завершено):** UI, approve/reject, атомарне створення доставки та захист від подвійного підтвердження.
6. **Доставка (завершено):** надійний мок, `5xx`, таймаути, втрачене HTTP-підтвердження,
   стабільний ключ ідемпотентності; відсутність доставки до approve і після reject.
7. **Локальну перевірку завершено:** наскрізні тести, чистий запуск, README, фінальний огляд.
   GitHub-репозиторій опубліковано за погодженням користувача:
   [Qwerty-polo/ai-first-support-service](https://github.com/Qwerty-polo/ai-first-support-service).
   Необов'язковий публічний деплой ще не виконаний.

Конкурентні гарантії перевіряти на PostgreSQL. Навантажувальні та масові сценарії
виконувати з контрольованим LLM, без платних викликів.
